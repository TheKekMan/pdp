# Монолит vs Микросервисы & Монорепозиторий vs Мультирепозиторий

## 1. Монолит vs Микросервисы

### Скрытые затраты (Hidden Costs)

| Критерий | Монолит | Микросервисы |
| :--- | :--- | :--- |
| **Сложность разработки** | Низкая (единая кодовая база, прямой вызов функций). | Высокая (сетевые вызовы, ретраи, таймауты, автоматические выключатели / Circuit Breakers). |
| **Консистентность данных** | ACID транзакции «из коробки» на уровне СУБД. | Eventual Consistency. Необходимость внедрения паттернов Saga или 2PC (Two-Phase Commit). |
| **Инфраструктура и DevOps** | Дешево и просто. Один CI/CD пайплайн. | Дорого. Необходимы Service Mesh, централизованное логирование (ELK/Grafana Loki), распределенный трейсинг (Jaeger/OpenTelemetry), API Gateway. |
| **Тестирование** | Простое сквозное тестирование в рамках одного процесса. | Сложное интеграционное тестирование. Необходимость контрактного тестирования (например, Pact). |
| **Организационные затраты** | Минимальные при небольшом штате. | Высокие (закон Конвея). Требуются автономные кросс-функциональные команды. |

---

### Признаки необходимости дробления монолита (Split Signals)

1. **Организационное бутылочное горлышко (Team Bottleneck):**
   * Разные команды постоянно коммитят в один и тот же модуль, вызывая конфликты слияния (merge conflicts) и блокировки релизов.
   * Очередь на релиз растягивается, так как баг в одной фиче блокирует деплой всего приложения.

2. **Неравномерная нагрузка (Scale Asymmetry):**
   * Один модуль (например, генерация отчетов или обработка видео) требует 90% ресурсов процессора/памяти, из-за чего приходится масштабировать весь монолит, что экономически неэффективно.

3. **Разные требования к надежности (Fault Isolation):**
   * Падение критически неважного сервиса (например, рекомендаций товаров) валит все приложение, включая оплату и корзину.

4. **Технологический тупик (Tech Stack Lock):**
   * Для новой задачи (например, Machine Learning) необходим Python, а весь монолит написан на PHP/Node.js, и интеграция внутри одного процесса невозможна.

## 2. Монорепозиторий vs Мультирепозиторий

### Скрытые затраты (Hidden Costs)

| Критерий | Монорепозиторий (Monorepo) | Мультирепозиторий (Polyrepo) |
| :--- | :--- | :--- |
| **Масштабирование инструментов** | Огромные затраты на кастомный тулинг. Обычный Git начинает тормозить на гигабайтных репозиториях. Необходимы кэширующие билд-системы (Turborepo, Nx, Bazel). | Простота стандартных инструментов. Каждая кодовая база изолирована и мала. |
| **Управление зависимостями** | Single Version Policy (все проекты используют одну версию React/Express). Обновление общей зависимости может сломать десятки проектов одновременно. | Dependency Drift. Проекты используют разные версии общих библиотек. Обновление превращается в рутину с десятками Pull Request'ов. |
| **Границы доступа (Security/Permissions)** | Сложно разграничить права доступа. Разработчик видит весь код компании. | Четкие границы. Разработчик имеет доступ только к тем репозиториям, над которыми работает. |
| **Ревью кода и CI/CD** | При изменении в одном месте пайплайн может запускать тесты для всего монорепозитория, если не настроен инкрементальный сборщик. | Простой CI/CD для каждого репозитория. Но сквозные изменения требуют скоординированного деплоя нескольких сервисов. |

---

### Признаки необходимости дробления монорепозитория

1. **Технические лимиты Git и IDE:**
   * Время `git status` или `git fetch` превышает несколько минут.
   * IDE (VS Code / WebStorm) индексирует проект часами и потребляет гигабайты ОЗУ.

2. **Организационная автономия:**
   * Команды имеют абсолютно разные циклы релизов, политики безопасности и стандарты качества.
   * Безопасность требует жесткого ограничения доступа к исходному коду (например, аутсорс-команды не должны видеть ядро системы).

3. **Сложность CI/CD инфраструктуры:**
   * Поддержка Turborepo/Nx/Bazel конфигураций начинает отнимать больше времени у DevOps-инженеров, чем разработка продуктовых фич.

## 3. Рекомендуемые источники для изучения

1. **Микросервисы:**
   * [Martin Fowler - Microservices Guide](https://martinfowler.com/articles/microservices.html) — фундаментальная вводная статья об архитектуре микросервисов от Мартина Фаулера.
   * [Microservices.io](https://microservices.io/) — полный сборник паттернов проектирования микросервисов (Saga, API Gateway, Event Sourcing).
2. **Монорепозитории vs Мультирепозитории:**
   * [Monorepo.tools](https://monorepo.tools/) — отличный путеводитель по миру монорепозиториев со сравнением инструментов (Turborepo, Nx, Bazel).
   * [Turborepo Documentation](https://turbo.build/repo/docs) — руководство по оптимизации кэширования и сборки проектов.
