# Стратегия тестирования фронтенда

Успешная стратегия тестирования строится на балансе скорости выполнения, стоимости написания/поддержки и уверенности (confidence), которую дают тесты.

## 1. Виды тестирования

### Тестирование снапшотами (Snapshot Testing)
* **Проблема:** Разработчики пишут тесты, которые просто сохраняют HTML-структуру компонента и сверяют её при каждом запуске.
* **Когда использовать:**
  * Тестирование чисто презентационных компонентов (дизайн-система, UI-kit, иконки).
  * Тестирование конфигурационных файлов, сериализованных данных или JSON-ответов API.
* **Почему начинает приносить вред (хрупкость):**
  * Снапшоты часто обновляют не глядя (`u` в Jest/Vitest), когда они ломаются от изменения стилей или мелких правок разметки.
  * Они не проверяют поведение компонента (кликнул ли пользователь, открылась ли модалка).
  * Засоряют pull request'ы огромными diff'ами.

### Тестирование логики компонентов (Component Behavior Testing)
* **Решение:** Тестирование взаимодействия пользователя с компонентом (через Testing Library).
* **Принцип:** Тестировать компонент так, как с ним взаимодействует реальный пользователь (поиск по тексту, ролям, плейсхолдерам, а не по внутреннему состоянию или классам CSS).
* **Что тестировать:**
  * Вызываются ли правильные колбэки при клике/вводе.
  * Отображаются ли сообщения об ошибках при неверном вводе.
  * Условный рендеринг (Spinner во время загрузки, ErrorBoundary при сбое).

### Сквозное тестирование (E2E Testing)
* **Решение:** Проверка всей цепочки работы приложения (от ввода логина на фронтенде до записи в реальную/тестовую БД на бэкенде) в реальном браузере.
* **Плюсы:** Дает максимальную уверенность в работоспособности системы.
* **Минусы:** Медленное выполнение, хрупкие тесты (flaky tests), сложная настройка инфраструктуры и тестовых данных.

## 2. Сравнение инструментов: Vitest vs Jest vs Playwright

| Инструмент | Тип тестов | Плюсы | Минусы | Когда выбирать |
| :--- | :--- | :--- | :--- | :--- |
| **Vitest** | Unit / Integration | - Нативная интеграция с Vite (общие конфиги, плагины).<br>- Экстремально быстрый запуск (благодаря ESM и HMR).<br>- Полная совместимость с API Jest. | - Относительно молодой проект.<br>- Меньше готовых сторонних интеграций, чем у Jest. | Для любых новых проектов на Vite или React-приложений с быстрыми юнит-тестами. |
| **Jest** | Unit / Integration | - Огромная экосистема, проверен временем.<br>- Отличная документация. | - Сложная настройка TypeScript/ESM (требуется Babel/ts-jest).<br>- Медленнее на больших проектах из-за отсутствия ESM-оптимизаций из коробки. | Для легаси-проектов или крупных Enterprise-решений, где уже выстроена инфраструктура на Webpack/CRA. |
| **Playwright** | E2E / Component | - Запуск в реальных браузерах (Chromium, Firefox, WebKit).<br>- Генератор тестов (Codegen).<br>- Встроенный Trace Viewer (пошаговая отладка сквозного сценария с DOM-скриншотами).<br>- Авто-ожидание элементов (нет нужды в `sleep`). | - Требует установки браузеров (большой вес).<br>- Ресурсоемкий (требует хороших CPU для параллелизации). | Основной инструмент для E2E и тяжелого интеграционного тестирования современных веб-приложений. |

## 3. Рекомендуемая пирамида (трофей) тестирования

Для современного React-приложения оптимален подход **Testing Trophy** (Кент С. Додс):

```
       / \
      /   \      - E2E Tests (Playwright): ~10% (критические пути: регистрация, оплата)
     / E2E \
    /=======\
   /         \   - Integration/Behavior Tests (Vitest + Testing Library): ~60%
  /  Integr.  \    (проверка страниц и ключевых фич)
 /=============\
/     Unit      \ - Unit/Static Tests (Vitest / TypeScript / ESLint): ~30%
-----------------   (чистые функции, хелперы, утилиты, типы)
```
