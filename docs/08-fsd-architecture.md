# Архитектура FSD (Feature-Sliced Design) и альтернативы

## 1. Зачем нужен FSD?

**Главная проблема классической слоистой архитектуры (folders-by-type):**  
При росте кодовой базы папки `components/`, `hooks/`, `utils/` разрастаются до сотен файлов. Теряется контекст (какой хук к какой странице относится), возникают неявные циклические зависимости, а рефакторинг становится опасным.

**FSD решает это путем:**
1. **Явного разделения по зонам ответственности (Layers).**
2. **Изоляции модулей (Slices).**
3. **Контроля направления импорта (сверху вниз).**
4. **Инкапсуляции логики за Public API (файлы `index.ts`).**

---

## 2. Структура FSD

Приложение делится на 6 слоев (Layers), расположенных по иерархии (от верхнего к нижнему):

1. **`app/`** — инициализация приложения (провайдеры, глобальные стили, роутинг).
2. **`pages/`** — страницы приложения (композиция виджетов в полноценные экраны).
3. **`widgets/`** — крупные самостоятельные блоки страниц (например, `Header`, `Sidebar`, `ProductGrid`).
4. **`features/`** — действия пользователя, несущие бизнес-ценность (например, `AddToCart`, `LikePost`, `SearchProducts`).
5. **`entities/`** — бизнес-сущности (например, `User`, `Product`, `Order`). Содержат UI-карточки сущности, схемы данных, стейт и API-запросы.
6. **`shared/`** — переиспользуемый технический UI и утилиты (UI-kit, API-клиенты, хелперы дат).

> **Золотое правило импорта:** Модуль может импортировать код только из нижележащих слоев. Например, `entities/User` **не может** импортировать что-либо из `features/` или `pages/`.

## 3. Альтернативные подходы

### А. Layered Architecture (Слоистая архитектура / По типам)
* **Структура:** `components/`, `hooks/`, `services/`, `utils/`, `pages/`.
* **Плюсы:** Идеально для небольших проектов (до 10-15 страниц), быстрый старт.
* **Минусы:** Спагетти-код при росте проекта, сложность масштабирования.

### Б. Domain-Driven Design (DDD) во фронтенде (По фичам / Domain-first)
* **Структура:** Группировка кода вокруг доменных областей (например, `/checkout`, `/catalog`, `/auth`). Внутри каждого домена лежат свои компоненты, хуки и стейт.
* **Плюсы:** Высокая сплоченность (high cohesion) кода по бизнес-смыслу. Команды могут владеть конкретными доменами.
* **Минусы:** Размытые границы между техническими компонентами общего назначения и бизнес-логикой.

## 4. Как адаптировать архитектуру под проект (Pragmatic Architecture)

FSD — это не догма, а конструктор. Настройка архитектуры под требования:

1. **Пропуск слоев (для MVP и простых проектов):**
   * Если проект небольшой, слой `widgets` часто избыточен. Можно собирать страницы напрямую из `features` и `entities`.
   * Если сущность не имеет сложной логики, не обязательно создавать для нее `entities/` — можно обойтись общей моделью в `shared/`.

2. **Простые проекты без FSD:**
   * Не внедряйте FSD для лендингов, простых сайтов-визиток или прототипов. Накладные расходы на создание структуры папок и `index.ts` файлов превысят пользу.

3. **Правило "Сначала shared/features, потом рефакторинг":**
   * Если вы не уверены, куда положить компонент — положите его в `features` или локально в папку страницы. Переносите его в `entities` или `shared` только тогда, когда он реально понадобится в других частях приложения.

   * [Khalil Stemmler - Software Design & Architecture](https://khalilstemmler.com/) — подробные гайды по применению принципов Domain-Driven Design и Clean Architecture на клиенте.
